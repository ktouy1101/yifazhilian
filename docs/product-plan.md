# 医法智联产品决策与实施计划

更新日期：2026-10-17。本计划汇总已确认方案及逐模块实施状态；M11 主流程已完成本机自动化验证，详见[M11使用与验收](m11-acceptance.md)。架构、接口边界见[技术设计](architecture.md)，项目来源见[调研记录](research.md)，分阶段安排见[实施路线图](implementation-roadmap.md)，实际启动与完成范围见[根说明](../README.md)。

## 1 项目目标与固定约束

项目为“智能医疗合规中的法律风险防控机制研究——基于数字化转型下患者权益保护的视角”。医法智联面向住院患者，结合健康信息、医学咨询、法律援助和院内导诊，帮助患者理解信息、核对依据、控制授权并找到人工帮助。预置演示使用虚构患者王*兰，女、72岁、心内科12床、青霉素过敏，紧急联系人为女儿。2026-10-18用户明确M03应上传本人的真实检验单，产品文案、告知及接口字段同步调整；不再将“必须是虚构资料”作为M03上传要求。

前端固定采用原生微信 WXML/WXSS/JavaScript，保留附件原型的健康、导诊、法援、我的四个入口和独立聊天页。后端采用 Python FastAPI 模块化单体、本机 SQLite，便于复用 OCR 与检索工具，避免学生阶段先部署微服务、图数据库或医院 ERP。模型通过可替换 Provider 接口接入；本地模板免费运行，用户主动配置的外部模型按其账户额度使用，不是默认必需依赖。

AR 必须交付，先做一家医院试点，可拍摄现有公共区域，不能新增二维码或标识。志愿者采集和审核员入口位于同一小程序，不独立建设管理平台。家属首期只在患者在场时同设备协助，不另建家属端，不自动获得病历或代签权。

## 3 模块规格

### M01 原生界面与适老化

**状态：已有界面，持续完善。** 输入为患者选择和服务真实状态，输出为可读卡片、清晰操作与错误恢复；依赖各业务模块。保持统一品牌、足够字号和大点击区域，关键操作同时有文字和状态说明，不能仅靠颜色。姓名遮罩与简短演示标签常驻，不让大段提示占据首屏。

健康页优先展示过敏、采样时间与来源、今日用药和医学咨询；法援从实际权益问题进入，原文依据可展开；我的承载病历、授权、设备与联系人。**验收：**老人可从四个主入口找到目标；断网、拒绝相机和服务失败有明确下一步；失败不会变为模拟成功。默认离线体验，不自动登录和授权。

### M02 身份授权与同设备家属协助

**状态：用途授权及撤回已有，真实身份和完整证据链待做。** 输入为身份、资源、用途、字段、接收方、期限与政策版本，输出为允许或拒绝及记录；所有私有模块依赖本模块。L1/L2/L3只作为界面预设，不能代替服务端逐项权限。

“我的→设置→连接本机服务”由用户主动操作；接收方或告知版本变化需重新授权。健康、病历、外部AI授权均按用途记住30天，登录会话保持30天；同意一次后，有效期内不再重复弹告知。外部问答仅发送当次合成问题和命中参考，不发送病历、体征、用户标识或历史。请求前和保存回复前重新核验；撤回阻断后续请求和进行中回复的保存返回，已发送请求无法收回。

家属协助只记录“同设备协助”及患者确认，不能据此建立已实名代理人审计或代签证明。**验收：**跨用户拒绝；重启不恢复已撤回授权；拒绝一个用途仍可使用无关功能；角色由后端确定，隐藏按钮不能替代鉴权。

### M03 病历本地 OCR 与版本

**状态：本机主流程已实现并通过自动化验收。** 输入为照片、核对字段，输出为待核对结果与确认版本；依赖M02和私有文件存储。入口“健康→检验单与病历”，流程为拍照/选择→预览与遮挡确认→本机OCR→原图定位对照→逐项确认→版本归档。采用独立Python 3.12 worker运行RapidOCR 1.4.4，模型随安装包预置；首次合成报告实测约3.2秒提取5项，原始单位符号有误识别，仍须逐项核对。PaddleOCR对照基准、复杂手写报告与真机验收未完成。“本地”指电脑端处理，不表示手机离线识别。2026-10-20 增加病历完整性清单：门诊/住院/复诊三种场景，按已归档资料区分缺少、待核对和已归档；医学智能体可回答“还缺什么”，但只判断资料类型，不判断医院诊疗完整性。详见[M03验收](m03-acceptance.md)。

记录资料类型、日期、机构、结果、单位、参考区间；低置信度醒目标记，保留原识别值、更正值和修改记录。未经确认结果不进入个体回答依据。**验收：**错误数值可改、版本可回查；失败可重拍或手填；取消不显示已保存；他人无法读取原图；拍照件不冒称医院认证副本。

### M04 健康记录与用药管理

**状态：无设备版本已实现，详见[M04使用与验收](m04-acceptance.md)。** 依据2026-10-18确认的范围，优先服务没有设备或医院接口的用户。健康Tab用“用药计划 / 健康状况”两个Tab切换，默认打开用药计划。“健康状况”首屏优先展示最近一次已归档的就诊/检查资料（仅在病历授权有效时聚合核对字段）、最近感受、用药与复诊摘要和“想问医生”入口，下方是检验单与病历、就诊摘要和复诊待办；手动心率、血氧、成对血压只在已有记录时显示，不制造空仪表盘。保留实际测量时间、来源与备注；以7/30天离散测量点展示变化。未测量时段不补值，不把旧值标为当前正常，也不自动作临床异常判断。2026-10-20新增7/30天“就诊摘要”，把本人测量、身体感受、用药执行和未完成待办汇总为可复制文本，只做记录整理，不计算依从率或判断疗效。

每日固定时间用药计划与本人服药记录分开。支持药名、规格、每次用量、多个时间、起止日期、暂停/结束；用户明确记录已服用、已跳过、未记录或稍后处理，已服用需要实际时间。修改计划保留过去时段与已报记录的药品用量快照。复诊等待办可创建、完成、删除。手机日历为用户主动添加单次提醒，小程序不承诺关闭后的采集或微信推送。

**验收：**健康授权撤回/过期后拒绝访问，切换身份清空页面；重复保存不重复生成，冲突先刷新核对；手填不标成设备采集，旧版演示读数不混入；旧药品迁移为待核对的暂停计划；未记录不等于漏服。未来设备、院内接口、连续监测和医护异常阈值作为独立扩展，具备真实数据渠道和处理能力后再接入。

### M05 医学智能体

**状态：单轮医学知识科普智能体第一版已闭环；跨轮上下文、个体数据工具和完整工作流待做。** 作用仅限“解释医生的话、按医嘱提醒、特殊情况提示”，不诊断、不开药、不调药、不替代就诊；输入为问题和经授权选取的信息，输出为分类、解释、合并后的追问建议；公共问答必需M02和M07，M03/M04个体数据及M08人工工具完成后才按需启用。工作流为风险提示→分类/主题→边界拦截→同域检索→解释与下一步，先做可测试的固定流程，再按复杂度考虑LangGraph。

2026-10-20 在现有 M05 聊天内加入本地分支，不新开页面或接口：患者问“看不懂诊断/是不是误诊/复诊/停药/检查结果”时，由本地规则解释其消息中描述的诊断为患者转录，不判断诊断对错；误诊、责任、赔偿和用药调整明确拒绝或转人工；有复诊待办时提醒复诊；出现胸痛、呼吸困难等危险信号立即劝导现场医护。该分支不调用外部模型，只使用公开医学知识和已授权的健康记录/复诊待办，检索只在服务端内部使用，不再展示来源。健康页同时根据近期身体感受记录和未完成复诊待办显示主动提示条，点击可带着问题进入同一医学聊天页；提示条只做提醒，不判断病情。另新增本地病历清单分支：在有效病历授权下，按门诊/住院/复诊资料类型回答“还缺什么”，区分未上传、待核对和已归档，不判断医院诊疗完整性。

2026-10-21 将 M05 第一版做成固定“分类→边界→检索→生成”链路：`services/medical_agent.py` 识别急症、紧急、诊断、用药、检查/手术、症状、生活方式等类别和医学主题；急症先劝现场求助，个人诊断/停药换药/剂量问题明确拒答；普通问题检索已发布医学片段后交给 Provider，回答正文不列来源；追问与问医生问题由后端合并去重为 `suggestions`（该字段 2026-10-24 已删除），聊天页只展示一套可点击建议；急症和个人诊断边界只给行动提示，不硬塞追问。知识库扩为 13 个医学演示来源、128 个片段，覆盖检验进阶、常见症状、常见病（含房颤、心衰、胆囊炎、胰腺炎、阑尾炎）、常用药、检查/围手术期、住院安全、出院随访、特殊人群和预防。主题与追问建议保存在 `message_metadata`，历史只还原公开字段。仍是单轮问答，不读取病历正文、不做跨轮追问、不接医院知识库或向量检索；详见[M05验收](m05-acceptance.md)。

每轮保存状态、使用工具与证据版本；急症提示不等待模型，也不让模型自动触发SOS。**验收：**缺乏依据时说明不足；不会自动诊断、开方或改病历；超时可恢复对话；撤回阻断资料工具；来源和当前演示能力清晰可见。

### M06 法律智能体

**状态：单轮法律知识智能体第一版已闭环；事实梳理、多轮槽位和真实人工工具待做。** 输入为患者描述和其主动选取的材料，输出为问题分类、参考条文、材料清单和下一步；公共问答必需M02和M07，病历读取与人工接手分别在M03、M08完成后启用。流程为事实梳理→区分医疗事实与权益问题→按时间和效力检索→大白话解释→必要时转专业人员。

2026-10-21 将 M06 做成固定“分类→安全边界→本地法条指引/同域检索→引用→材料与下一步”链路：`services/legal_agent.py` 识别知情同意、病历、隐私、纠纷、责任、赔偿和超范围问题；知情同意/病历/隐私/纠纷走本地审校文字，责任与赔偿明确拒绝判断，暴力威胁先劝报警/120，超范围转 12348 或律师；一般法律问题才检索已发布法律片段并交给 Provider。法律库扩为 3 个演示来源、20 个片段。聊天页显示主题、3 条追问、材料清单、下一步和问医务科/律师清单，历史消息保存 `message_metadata`。仍是单轮问答，不做跨轮事实梳理、不读病历正文、不生成正式法律意见；详见[M06验收](m06-acceptance.md)。

医学、法律分开提示词、工具、知识域和会话。跨域问题提示切换，患者确认摘要后新建会话，不默认复制全部病历或历史。**验收：**不串库、不编造条号；失效资料不当现行依据；建议与事实分开；未经专业处理不能宣称已确定责任或赔偿。

### M07 知识库 RAG 图谱与 MCP

**状态：第一版SQLite已发布知识库与引用已实现（2026-10-20）；知识运营、图谱、向量和完整MCP编排待实施。** 输入为可核实法规、经审核健康材料和关系证据，输出为带版本的片段与关联路径；依赖M02并服务M05/M06。记录来源URL、发布/生效/失效日期、机构、版本、审核人和片段位置；知识需审核发布，更新不覆盖历史引用。当前实现的检索规则、引用字段、可选法律只读MCP和限制见[M07说明](m07-acceptance.md)。

图谱先用SQLite节点与边表达“问题—权利—法条—材料”和“症状—科室—检查/注意事项”，每条边关联来源，连线不是诊疗或法律结论。公共知识和患者私有记录/图谱分开；后续向量索引也必须保留所有者和用途过滤。

MCP是工具连接协议，不是模型或准确性认证。首批只考虑本地只读法条工具，限定工具白名单、参数、超时、返回量，不直接传患者全文；医疗MCP暂无确定的必选实现。**验收：**来源能回查；停用知识不再检索；提示注入不能更改权限；工具失败明确返回，不伪造命中。

### M08 人工接手与文书

**状态：志愿者、律师与文书入口为演示，服务闭环待做。** 输入为患者预览确认的摘要、请求或文书草稿，输出为接单状态、审核版本与归档状态；依赖M02及真实接收人。志愿者限导诊、流程和陪伴，只见会合点及辅助需求；医护或律师读取资料需要对应资格和授权。

首轮交付文书草稿和人工工单闭环。同小程序设置按权限开放的接单页，后端核验接收人角色/资格、所属医院、工单归属和可见字段，患者只共享确认后的摘要。工单区分待接单、已接单、处理中、结束、失败与取消；无真实接收人不能显示“正在查看”。医疗文书与数据授权分开；正式签署须在真实渠道、资质及验签条件齐备后另接，覆盖医生审核解释、患者或核验代理确认及归档，内容变化生成新版本。**验收：**不能跳过审核；图片或哈希不自动等于可靠签署；人工请求失败保留摘要供患者再处理。

### M09 独立 SOS

**状态：本机接收演示已有，真实投递待做。** 输入为患者明确长按及幂等键，输出为事件和每个接收对象的真实状态；不依赖AI或病历授权。维持长按1.2秒、松手/隐藏取消、防重复与安全重试。

区分本机接收、开始投递、接收方确认、失败和取消。多对象通知不等于手机自动同时拨号；真实接通必须来自真实渠道。**验收：**重复请求不创建多次事件；无回执不显示已接通；网络或服务失败提示实体呼叫铃、病区服务台等实际路径。

### M10 地图包与 AR 定位导航

**状态：当前提供已发布路线的照片导览，演示轨迹已移除；地图包、定位和真实AR均待实施；AR为必做项。** 输入为已审核地图、目标和相机/姿态观察，输出为路径、可信定位及AR指引；依赖M11、设备能力和现场验证。首个试点以单楼层少量高频路线开始，明确科室入口、无障碍条件、单向通道和封闭路段。

利用现有门牌、导向牌及稳定场景作自然地标，结合平面图、测量和人工校准建立节点坐标、朝向与路线边。地图包包含医院/楼栋/楼层、版本、节点、边、距离、地标、参考照片、审核及实走时间。对准登记地标确认起点，在短路段跟随AR，漂移或关键转弯时重定位；现有门牌OCR只能辅助确认地点，不能单独解算完整相机位姿。

定位不可信立即暂停世界坐标箭头，提示重新校准或查看平面路线。开始与恢复导航时检查地图版本，收到停用立即停止受影响指引；缓存包有有效期，离线过期禁用导航，不承诺离线能即时收到停用。VPS保留为候选，先验证微信兼容、费用、本地运行、导出与许可，不把商业SDK样例当免费默认依赖。**验收：**在选定手机现场完成起点—转弯—终点；遮挡、丢失能恢复；轮椅路线不走楼梯；记录设备和地图版本。静态箭头、上传照片和模拟轨迹不能算AR验收。

### M11 志愿者采集审核与用户反馈

**状态：领取→拍照→提交→他人审核→发布/停用主流程已实现并通过本机自动化验证，真机与医院现场验收待做。** 输入为领取任务后的节点照片、路线说明与用户反馈，输出为待审材料、退回意见和发布版本；依赖M02，供M10使用。普通用户提交封闭、搬迁、错路、指示不清反馈；志愿者分段采集；审核员在同一小程序审核，服务端禁止自审，不建额外ERP。已提交内容与旧照片保留快照；已支持将历史版本恢复为新草稿，先撤下当前路线，重新提交并独立复核后发布；任务同步回到采集中。

导诊首页直接检索已发布路线，核对起点后进入手动照片导览；已注册工作台、逐节点采集、审核与照片导览页面；角色由服务端分配，演示切换明确标合成身份。导航访问不依赖患者AI用途授权，切换身份取消旧请求；草稿按所有者隔离。上传前预览，可调用微信照片编辑或重拍，不支持编辑的设备提示重拍；仅采允许公共区域，避开患者、人脸、腕带、病历和屏幕。照片去除EXIF/GPS，未发布原图不公开。

审核检查清晰度、方向、重复地标、楼层、隐私和路线连续性；发布前由另一人实走，记录障碍和无障碍条件，勾选只能记录人工声明。采集资料发布不等于AR标定，初期明确`ar_ready=false`。路线标明核验时间和版本；严重反馈可停用，发布可回滚，旧版本保留回查。**验收：**未发布材料不向患者公开；采集者不能自审；重复提交不重复发布；并发修改冲突有提示；停用路线退出当前列表；上传不是自动建图。

## 4 分阶段顺序与交付约定

实施统一按[路线图](implementation-roadmap.md)的步骤1—7：身份授权与数据基础→导航采集和小程序内审核→医院地图与真实AR试点→本地病历OCR核对→双知识库与双智能体→用药体征和紧急求助→整体联调。导航与AR为主线，步骤2同时验证一条短路线的真实AR可行性，不等采集做完才研究定位。OCR、知识库与健康线可在基础完成后并行；本轮不实施这些新增模块。

每个模块先用合成数据和假外部服务完成请求、成功、失败、取消、撤回及重试的验收，再单独评估真实接入。测试使用临时数据库，不清空日常演示库；页面数、接口数和测试通过不能代替临床、现场或接收方真实验收。后续每次交付更新当前范围、未完成项和可复核结果。

## 5 真实接入前的共同条件

姓名和电话显示遮罩；身份标识用内部ID，令牌和密钥不进入日志或前端；病历正文、影像、疾病、用药、体征、精确位置及其派生信息受私有权限保护，真实资料需加密存储。去掉姓名不等于匿名化；默认不采身份证和人脸。公开知识与地图包不能混入患者资料，原始照片也不能因为来自公共走廊就直接公开。

接入前须明确医院允许的采集范围、微信与院内身份关系、志愿者/审核员资格、患者告知授权、资料保留删除、外部服务处理范围、知识专业审核、签署验证和通知接收人。HTTPS、平台配置、备份恢复、撤回清理和访问审计需实际验证；家属联系人身份不构成代理资格。AR需真实场地和设备条件，不能用本机演示宣称定位精度。免责声明不能代替这些流程。
